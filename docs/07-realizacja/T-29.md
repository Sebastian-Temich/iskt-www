# Raport T-29: QA M2: zdublowany klucz build w astro.config.mjs po #22 i #23

Issue: #29
PR: #30

## Co zrobiono

- **Jeden klucz `build`, lint i typecheck zielone**: w `astro.config.mjs` został jeden klucz
  `build: { inlineStylesheets: 'never' }` z komentarzem o powodzie (CSP). `pnpm lint` (bez
  `no-dupe-keys`) i `pnpm typecheck` (bez TS 1117) przechodzą.
- **CSP bez zmian**: `vercel.json` nietknięty, `style-src 'self'` bez `'unsafe-inline'`.
  `e2e/csp.spec.ts` przechodzi w chromium i webkit.
- **Test wydajności zgodny ze sposobem ładowania CSS**: w `e2e/qa/QA-M1-1-wydajnosc.spec.ts` test
  „CSS wbudowany” zastąpiony testem „CSS z plików _astro/*.css tego samego źródła, bez <style> inline”:
  brak elementów `<style>`, co najmniej jeden `link[rel=stylesheet]`, każdy z tego samego źródła i ze
  ścieżką `/_astro/*.css`, token `--color-primary` ustawiony (style działają). Przechodzi w chromium
  i webkit; pełne `pnpm test:e2e` zielone.
- **Lighthouse na stagingu po merge'u**: do wykonania po merge'u (staging budowany z `main`). Wynik
  działania tej zmiany jest taki sam jak obecnie na `main` (działał ostatni klucz, `'never'`), a pomiar
  QA M2 na stagingu z CSS w plikach dał mobile 98, 99, 96 (≥ 90). Patrz „Ryzyka”.

## Decyzje

- CSS wbudowany (`'always'`, T-22) czy CSS w plikach (`'never'`, T-23)? → `'never'`: CSP
  `style-src 'self'` bez `'unsafe-inline'` jest wymaganiem architektury, a wbudowany CSS wymagałby
  `'unsafe-inline'` albo hashy generowanych przy każdej zmianie stylów. W-10 jest spełnione również z
  CSS w plikach (Lighthouse mobile QA M2: 98, 99, 96).
- Co sprawdza test QA-M1-1 zamiast braku arkuszy? → brak `<style>` inline i arkusze wyłącznie z
  `/_astro/` tego samego źródła, bo to warunek zgodności z CSP i odwrotność poprzedniego założenia;
  sprawdzenie tokenu koloru zostaje.

## Drobne uwagi

- CI na push do `main` uruchamia tylko `check-dod`, więc konflikt dwóch PR-ów zielonych osobno
  (jak #24 i #27) nie jest wykrywany po merge'u. Warto uruchamiać lint i typecheck także na `main`
  albo wymagać aktualnej gałęzi przed merge'em.

## Ryzyka

- Kryterium Lighthouse 12.8.2 (staging, mobile, 3 przebiegi na `/`) da się sprawdzić dopiero po
  merge'u i wdrożeniu stagingu; przed merge'em go nie mierzyłem. Wyniki dopisuje orkiestrator albo QA
  po merge'u. Ryzyko niskie: wynikowy build jest taki sam jak obecnie na `main`, zmierzony w QA M2.

## Propozycje dla systemu

- Kryteria wymagające pomiaru „po merge'u” (np. Lighthouse na stagingu) nie mogą być spełnione przez
  workera przed review. Propozycja: w szablonie issue oznaczać takie kryteria jako weryfikację
  orkiestratora/QA po merge'u albo dodać krok `shctl` do pomiaru po merge'u.
